# machin3d-overlay 3.0.0

Two big things this release: the project is renamed to `machin3d-overlay`
(see [v2.0.0 release notes](v2.0.0.md) for the previous identity), and
Snapmaker U1 is now supported as a first-class second printer vendor
alongside Bambu Lab. The CLI flag namespace and the on-disk state directory
move accordingly. Existing 2.0.0 deployments need to update their install
paths, service units, and state-file locations — see the breaking-changes
section below.

## New: Snapmaker U1 support

Snapmaker printers running Moonraker (verified on the U1) are now peers of
Bambu Lab printers in every overlay surface:

- **`--snap-device HOST[:PORT]`** on `serve`: add one Snapmaker printer per
  flag. Startup probes `http://HOST:PORT/machine/system_info` for the
  printer's serial number (used as the stable device ID) and friendly name.
  Port defaults to `80`.
- **Per-device Moonraker WebSocket worker** subscribes to `print_stats`,
  `display_status`, `extruder[0..3]`, `heater_bed`, `fan`, `virtual_sdcard`,
  `print_task_config`, `gcode_move`, and `toolhead`. Status updates merge into
  a vendor-neutral `PrinterReport` and feed the same shared overlay state
  Bambu uses, so `/horizontal`, `/vertical`, `/api/current-print/events`,
  `/api/devices`, `/devices/<id>/thumbnail`, and `/devices/<id>/video.mjpeg`
  all work identically across vendors.
- **Thumbnails** for Snapmaker prints are downloaded through Moonraker's HTTP
  file API and cached on the same task-change trigger Bambu uses.
- **Per-slot filament color and type** are read from
  `print_task_config.filament_color_rgba` / `filament_type` and shown in the
  overlay's material tiles.
- **Klipper speed factor** is shown in the print-speed tile, and the
  part-cooling fan speed flows through to the fan tile.
- **`serve` no longer requires a Bambu Cloud token file.** Snapmaker-only
  deployments work without ever running `login`.

### `snap-pair`: reliable camera wake-up

The U1's on-device camera daemon only writes fresh frames to `monitor.jpg`
while it is in "monitor" mode; by default the file is frozen on the last
captured frame. A new `snap-pair` subcommand drives the same bespoke mTLS
MQTT control plane Snapmaker Orca uses to wake the daemon on demand:

```sh
# Switch the printer into LAN mode first (Settings → Network) to expose
# the approval popup. Cloud mode can be turned back on after pairing.
machin3d-overlay snap-pair 192.168.1.60   # tap "Approve" on the printer screen
machin3d-overlay serve --snap-device 192.168.1.60
```

`snap-pair` runs the cleartext-MQTT bootstrap on `:1884`, prints a tap-Approve
prompt, and on approval writes the printer-issued client cert/key/CA plus a
stable client ID to `$XDG_STATE_HOME/machin3d-overlay/snap-tokens.json` (mode
`0600`). `serve` loads this file at startup and opens a long-lived mTLS
session against the printer's `:8883` broker that publishes
`camera.start_monitor` on stream open and `camera.stop_monitor` on the last
client disconnect.

LAN mode is required **only for the initial pairing** — the issued cert keeps
working after the printer is switched back to cloud mode. Override the file
location with `--snap-token-file PATH` on both `snap-pair` and `serve` if you
need a non-default path.

Without `snap-pair`, the overlay still serves
`/devices/<id>/video.mjpeg` but does not attempt to wake the camera daemon;
frames will only update while another tool (a print job, Orca) keeps the
daemon active.

## Breaking changes

### Project renamed to `machin3d-overlay`

The binary, library crate, on-disk state directory, and example systemd unit
all change name. Update any of the following you have installed:

- **Binary**: the executable produced by `cargo build --release` now lives at
  `target/release/machin3d-overlay`. Move (or symlink) `/usr/local/bin/` or
  whatever path you install to under the new name; update `ExecStart=` in
  service units.
- **Library crate**: Rust embedders should change `use` paths to
  `use machin3d_overlay::…`. The internal module layout is unchanged this
  release.
- **XDG state directory**: token files and snap-pair material now live under
  `$XDG_STATE_HOME/machin3d-overlay/` (typically
  `~/.local/state/machin3d-overlay/`). No automatic migration is performed.
  To carry existing state across, `mv` the contents of the v2.0.0 state
  directory into the new one; otherwise re-run `login` and (for Snapmaker)
  `snap-pair`. Likewise the default `--bbl-token-file` and `--snap-token-file`
  paths follow the new directory name.
- **systemd unit file**: the example at `examples/systemd/` was renamed to
  match. Reinstall under the new filename and update `User=`/`Group=`/
  `StateDirectory=`/`ReadWritePaths=` references in your local copy if you
  followed the prior pattern of naming them after the project.
- **User-Agent string**: outbound Bambu Cloud API calls now identify
  themselves as `machin3d-overlay/0.1`. The MQTT client-ID prefix likewise
  changes. Neither value is contractually meaningful to Bambu Cloud, but
  log-correlation rules on your side may need updating.

### Bambu CLI flags moved into a `--bbl-` namespace

To make room for `--snap-*` flags without ambiguity, every Bambu-specific
flag gained a `--bbl-` prefix:

| 2.0.0 flag         | 3.0.0 flag             |
| ------------------ | ---------------------- |
| `--token-file`     | `--bbl-token-file`     |
| `--cloud-mqtt`     | `--bbl-cloud-mqtt`     |
| `--cloud-device`   | `--bbl-cloud-device`   |
| `--local-device`   | `--bbl-local-device`   |
| `--video-device`   | `--bbl-video-device`   |

Semantics, accepted values, and defaults are unchanged. Update any service
units, scripts, or shell aliases that pass these flags. The default token file
path is unchanged. The vendor-neutral `--bind`, `--timeout`, and `--device`
(on `mqtt`) flags keep their names.

### Library API

- The `bambu::CloudDevice` type is renamed to `bambu::BambuCloudDevice` to
  make the vendor explicit. Combined with the crate rename above, the full
  import is now `use machin3d_overlay::bambu::BambuCloudDevice;`.
- The internal `crate::mqtt::*` module moved to `crate::bambu::mqtt::*`; this
  is internal-only (the module is `pub(crate)`) but embedders that reached
  into it through a fork will need to update import paths.

## Other improvements

- The `/api/devices` JSON response now correctly labels Snapmaker devices as
  `"local"` (they were briefly mislabeled `"cloud"` during early Snapmaker
  development).
- The Snapmaker camera worker uses a tight `stop_monitor` budget on the drop
  path so it does not blow past the parent shutdown grace period.
- Successful Bambu video endpoints are still remembered for the process
  lifetime; mismatched endpoint/device pairs are remembered for re-tries.
- The repo's TLS dependencies are consolidated on `native-tls` (reqwest no
  longer pulls in the rustls + ring + webpki-roots + quinn stack).

## Internals (no user-visible behavior change)

- Per-vendor `DeviceCapabilities` enum (`Bambu { cloud, local }` /
  `Snapmaker { … }`) replaces the previous flat option-bag and the separate
  `Backend` discriminant. Vendor-specific dispatch is now type-checked.
- New top-level `src/bambu/` and `src/snapmaker/` namespaces hold every
  vendor-specific module (auth, cloud, device_tls, local, mqtt, report,
  models on the Bambu side; auth, pair, mtls, moonraker, report, backend,
  probe on the Snapmaker side).
- The PKCS#1→PKCS#8 conversion required for the Snapmaker mTLS private key
  goes through the `rsa` crate's `RsaPrivateKey::from_pkcs1_pem` +
  `to_pkcs8_pem` (replacing an earlier hand-rolled ASN.1 encoder).
- Cross-vendor helpers (`Endpoint`, `Secret<T>`, atomic state-file writer,
  error-chain formatter) live at the crate root.
- The `Endpoint` parser now returns a structured `EndpointParseError` rather
  than `anyhow::Error`.
